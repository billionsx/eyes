# Петля ревью · редакция BXE

## Чем отличается от первоисточника

Устройство петли взято целиком из `loop-code-review` (MIT, Dima Sukharev) —
дословная копия лежит рядом в `skills/loop-code-review/`, происхождение и
отпечатки в её `ORIGIN.md`. Департамент из сети её не тянет: копия в базе и
есть источник.

Отличие одно, и оно существенное. Там, где первоисточник говорит «прогони
подходящие тесты, линт и сборку», редакция департамента называет **конкретный
гейт с числами**:

```
python3 <BXE>/bin/loop.py start --root . --paths "<пути задачи>" \
        [--validated "npm test=0"] [--validated "tsc --noEmit=0"]
```

Гейт судит затронутую поверхность правилами AE1..AE18 — теми же, что стоят в
CI департамента, — и **блокирует только находки на строках, которые задача
добавила**. Находка на нетронутой строке называется отдельно как доставшийся
долг: требовать её снятия внутри чужой задачи значит навязывать работу, а не
судить работу.

Второе отличие — машинная приёмка. Таблица решений живёт не в тексте, а в
`bin/loop.py verdict`, и её нельзя обойти вежливой формулировкой.

## Порядок

1. **Объяви область.** Петля не угадывает принадлежность изменений. Пути
   задачи называются явно (`--paths`), остальное грязное дерево уходит в
   «исключено». Если принадлежность файла или куска правда неясна — спроси
   пользователя, не гадай.

   ```
   python3 <BXE>/bin/loop.py scope --root . --paths "src/a.tsx,src/a.css"
   ```

2. **Прогони гейт и получи промпт.** `start` печатает состояние гейта и
   готовый **самодостаточный** промпт ревьюера. Промпт отказывается строиться,
   если в него подмешан родительский контекст (`--extra` с «предыдущий
   ревьюер сказал…»): ревьюер, получивший чужие выводы, перестаёт быть
   независимым, и его подпись перестаёт что-либо значить.

3. **Запусти СВЕЖЕГО ревьюера.** Отдельный агент, чистый контекст, режим
   только чтения. Не продолжай прежний разговор ревьюера ради новой оценки —
   каждый оценочный проход делает новый ревьюер. Передавай ему ровно
   напечатанный промпт и ничего сверх него.

4. **Внеси вердикт.** Находки объявляются перечислением — орган не решает
   сам, что в абзаце было находкой:

   ```
   python3 <BXE>/bin/loop.py verdict --root . --paths "..." \
       --score 9.6 --finding "утечка ключа в лог, api.ts:42"
   python3 <BXE>/bin/loop.py verdict --root . --paths "..." \
       --score 9.7            # находок нет → ПРИЁМ
   python3 <BXE>/bin/loop.py verdict --root . --paths "..." \
       --score 9.0 --no-actionable   # явное «замечаний нет» → ПРИЁМ
   ```

5. **Чини, проверяй, повторяй.** После каждой значимой правки — снова гейт,
   потом снова свежий ревьюер. Петля закрывается только по `ПРИЁМ`.

## Таблица приёмки (исполняется машиной)

| состояние | решение |
|---|---|
| гейт красный — при любом балле | ПРОДОЛЖИТЬ |
| осталась действенная находка — при любом балле, включая 10/10 | ПРОДОЛЖИТЬ (**ЗКН-Э009**) |
| находок нет, гейт зелёный, балл ≥ 9.5 | **ПРИЁМ** |
| находок нет, гейт зелёный, явное «действенных находок нет» | **ПРИЁМ** |
| находок нет, балл ниже 9.5, явного сигнала нет | ПРОДОЛЖИТЬ: спросить ОДИН раз, что мешает планке |
| проходов ≥ 5 без приёмки | **НЕПОЛНО** — это незакрытая петля, а не успех |
| застой: поверхность не менялась, претензии те же | **НЕПОЛНО** |

`--persist` снимает предел проходов, когда пользователь требует дожать. Планку
он не опускает — планку не опускает ничто.

## Что говорить в конце

- что изменено и зачем;
- сигнал приёмки: балл ≥ 9.5, «замечаний нет» или оба;
- сколько было оценочных проходов и чем кончилось: ПРИЁМ, НЕПОЛНО, прервано;
- какие проверки прогнаны и с какими кодами возврата;
- оценка качества тестов, если тесты трогались;
- находки, сознательно не принятые, — с основанием;
- оставшийся риск.

## Границы

Петля судит **изменение**, а не проект. Полный проектный приговор — это
`eyes_scan` / `bin/eyes.py lint`. Петля не пишет код за исполнителя и не
раздаёт вкусовых советов: она предъявляет норму с адресом, а решение
остаётся человеку (ст. 7.4).
